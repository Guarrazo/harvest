# NCIG v0.12 — deterministic resource binding

NCIG plans are intentionally resource-light: the procedural generator can decide room geometry without knowing which concrete `.mesh` or `.ent` files exist on a particular Cyberpunk installation. v0.12 introduces an explicit binding step before native export.

## Inputs

The resolver accepts either `ncig-harvest-v1` output or `ncig-resource-catalog-v2`. It reads real resource paths and, when available, harvested role/source metadata.

## Decision order

1. An explicit resource already present on the node wins.
2. Exact semantic role matches receive the highest weight.
3. Filename/context agreement with the generated node is used to break ties.
4. Mesh/entity nodes are filtered to `.mesh`/`.ent`.
5. If nothing plausible exists, NCIG leaves the node unresolved and reports it.

This is intentionally conservative. NCIG never invents a DepotPath to make a report look complete.

## Audit commands

```powershell
python -m ncig.cli resource-check --plan build/generated/wb_plans/demo_shop_001_world_plan_v2.json --assets build/harvest.json --out build/resource_check.json
python -m ncig.cli bind-resources --plan build/generated/wb_plans/demo_shop_001_world_plan_v2.json --assets build/harvest.json --out build/bound_world_plan.json --report build/resource_bind_report.json
```

`resource-check` is read-only. `bind-resources` writes a copy of the plan and records its decisions under `ncigResourceBinding`. The native bridge strips NCIG-only metadata before producing its clean output.

## What v0.12 does not claim

A resolved resource path does not by itself prove that the corresponding World Builder node payload is valid for the installed exporter revision. Enum-heavy node types still prefer harvested real node templates. The remaining blocker for the first in-game shell is therefore verified templates from one real World Builder/entSpawner environment.
