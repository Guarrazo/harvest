# v0.19 — native architecture mesh export

NCIG v0.19 adds the first bridge from the real harvested architecture assembly to a native World Builder/Object Spawner JSON envelope.

The exporter is deliberately template-driven. It clones a real harvested `worldMeshNode` and changes only:

- `name` / `nodeRef`
- `position` / `streamingRefPoint`
- `rotation`
- `scale` when the assembly supplies one
- `data.mesh.DepotPath`
- `data.meshAppearance` only when the source placement explicitly provides one

Renderer/exporter enum values and other unknown payload members remain exactly as they appeared in the real probe template.

## Command

```powershell
.\tools\architecture_native_export_cp2077.cmd `
  build\generated\layouts.json `
  build\real_architecture_remote\architecture_assembly.json `
  build\mesh_probe_templates.json `
  C:\Users\Guarrazo\Desktop\mesh_probe.json `
  build\real_architecture_remote\ncig_architecture_demo.json `
  build\real_architecture_remote\ncig_architecture_demo.report.json `
  demo_shop_001
```

The `base` export supplies only the real top-level Object Spawner and sector envelope. Its probe nodes are discarded; NCIG emits only generated architecture mesh nodes.

## Current limitation

Architecture dimensions are still based on catalog hints. NCIG currently uses assembly scale only and does not invent mesh bounds or auto-scale from filenames. The generated native JSON therefore requires an in-game/WolvenKit bounds check before treating the architecture as final.

## One-command pipeline

After the first real mesh probe, the complete remote-harvest → native-template → native-export → native-audit flow is available as:

```powershell
.\tools\prepare_native_architecture_remote.cmd `
  https://github.com/Guarrazo/harvest `
  C:\Users\Guarrazo\Desktop\mesh_probe.json `
  C:\Users\Guarrazo\Desktop\mesh_probe.json `
  demo_shop_001
```

The probe JSON may be passed twice here: once to learn the native `worldMeshNode` template, and once as the real World Builder envelope/base schema. The probe nodes themselves are not copied into the generated architecture; only its envelope and the mesh-node schema are used.

The pipeline writes:

- `build\native_templates.json`
- `build\native_probe_report.json`
- `build\real_architecture_remote\native_architecture\demo_shop_001.json`
- `build\real_architecture_remote\native_architecture\demo_shop_001.report.json`
- `build\real_architecture_remote\native_architecture\demo_shop_001.audit.json`

The final audit must report `"passed": true` before the JSON is considered structurally clean for the next WolvenKit test.
