# NCIG v0.2 real-world workflow

NCIG v0.2 now models the real World Builder pipeline more closely. Cyberpunk's world is made from nodes grouped into streaming sectors, and ArchiveXL supports adding custom sectors without destructively editing the vanilla world. World Builder exports root groups as sectors and produces an Object Spawner JSON which WolvenKit converts to native `.streamingsector` / `.streamingblock` resources. The official workflow documents this JSON → WolvenKit conversion. 

## 1. Capture runtime entry points

Use RedHotTools in-game and collect observations for candidate doors. The current World Editing documentation says RHT can inspect nodes and provide node type, node instance and sector path. Export those observations to JSON using the shape illustrated in `examples/runtime_observations.example.json`.

Then:

```powershell
$env:PYTHONPATH="$PWD/src"
python -m ncig.cli scan `
  --input examples/runtime_observations.example.json `
  --out build/scan_report.json `
  --anchors-out build/scanned_buildings.json `
  --district watson
```

The scanner is deliberately heuristic. It identifies door-like nodes by name/type/instance/tags, groups nearby entries, and creates deterministic building anchors. Measurements that come from the real runtime should replace the default 10x10x1 assumptions before a city-scale pass.

## 2. Generate procedural interiors

```powershell
python -m ncig.cli generate `
  --input build/scanned_buildings.json `
  --out build/generated
```

The generated `*_world_plan_v2.json` files contain:

- modular architectural shell elements;
- floor/corridor/core planning;
- room and door sockets;
- a dedicated building-entry marker at the scanned anchor;
- gameplay/loot sockets;
- streaming-sector extents;
- node type names matching World Builder's current node model.

## 3. Connect actual resources

Run the asset catalog against a WolvenKit-extracted depot:

```powershell
python -m ncig.cli catalog `
  --root C:\CyberpunkAssets\Depot `
  --out build/resource_catalog.json
```

The catalog deliberately ranks `.ent` candidates for interactive props and `.mesh` candidates for architecture. It is still a heuristic catalogue; ambiguous assets must be reviewed once per semantic class, not once per building.

## 4. Native export boundary

NCIG does not fabricate CR2W internals. Its v2 plan is an authoring intermediate. The supported World Builder workflow exports a project to Object Spawner JSON, and WolvenKit imports that JSON to produce native sectors and blocks. Keep this boundary explicit until we have a verified mapping for the user's exact World Builder build.

Relevant World Builder node types for NCIG include static mesh, entity, collision, light, AI spot, community, interior area, ambient area and static marker nodes.

## 5. Runtime routing

The next runtime bridge will consume `ncig-entrance-routes-v1`. The preferred strategy is to reuse an existing door/node when possible and fall back to a proxy door only when required. The runtime layer should be a small Codeware/CET component; static architecture stays in streaming sectors.

## 6. Scaling rule

For city-scale generation, keep each floor or spatially distant sub-build as its own root group/sector. World Builder's documentation explicitly recommends separate root groups when distant parts should stream independently.
