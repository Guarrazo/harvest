# NCIG v0.4 — Exact Object Spawner bridge

The user's real World Builder export establishes the following envelope:

- `xlFormat: 0`
- `version: 1.0.4`
- `sectors[]`
- sector `min`, `max`, `variantIndices`, `nodes`, `variants`, `category`, `level`, `prefabRef`, `name`
- top-level `devices[]` and `psEntries[]`

The bridge now uses this envelope directly.

## Principle

NCIG never converts a logical `worldMeshNode` into a fake `worldEntityNode`. Instead it requires a real exported node of that type and clones it as the payload template. This is important because World Builder maps object categories to distinct engine node classes (Entity Template -> `worldEntityNode`; Static Mesh -> `worldMeshNode`; Collision Shape -> `worldCollisionNode`; Static Light -> `worldStaticLightNode`). citeturn227614search0

## Commands

```powershell
$env:PYTHONPATH="$PWD/src"
python -m ncig.cli exact-fingerprint `
  --input examples/ncig_probe_exported.json `
  --out build/exact_fingerprint.json
```

```powershell
python -m ncig.cli exact-bridge `
  --plan build/v03_demo/wb_plans/demo_shop_001_world_plan_v2.json `
  --template examples/ncig_probe_exported.json `
  --out build/demo_shop_001_exact_object_spawner.json
```

Because the supplied probe contains only `worldEntityNode`, the bridge will emit only NCIG nodes of that class and report every other required class under `ncig.skipped`.

## Why this is the correct limitation

The documented World Builder -> WolvenKit path exports JSON and then uses the `import_object_spawner` system script to create native `streamingBlock`/`streamingsector` files. citeturn446824search0 NCIG therefore stays at the exact JSON boundary until the project has real templates for each node class it needs.
