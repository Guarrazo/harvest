# NCIG v0.22.8 — city-scale world export pipeline

## Current input format

WolvenKit's JSON representation of a native `worldStreamingSector` uses a top-level `Data` object. Inside it, `nodes` contains distinct node definitions and `nodeData` contains the placement records. Each `nodeData` entry references a node by `NodeIndex`. WolvenKit serializes the `worldNodeDataBuffer` as structured JSON when that buffer type is recognized. citeturn480845view0

NCIG now parses this native structure directly instead of expecting an Object Spawner-style envelope.

## Persistent index

A large export should be indexed once:

```powershell
$py = Get-Command py.exe | Select-Object -First 1 -ExpandProperty Source
& $py -3 -m ncig.cli index-city-world --input C:\CyberpunkExports\sectors --out build\city_world_index.sqlite --manifest-out build\city_world_index_manifest.json
```

The index keeps only entrance, exterior-architecture and interior evidence plus compact transforms, dimensions and sector provenance. The original 90 GB export remains untouched.

Subsequent detection runs can read the SQLite index rather than reparse every sector:

```powershell
& $py -3 -m ncig.cli detect-city-buildings --input build\city_world_index.sqlite --out build\auto_building_candidates.json
```

The automatic preparation script now performs this indexing pass automatically when the database does not already exist.

## Single-sector smoke test

Before indexing the whole city, inspect one exported sector:

```powershell
$one = Get-ChildItem C:\CyberpunkExports\sectors -Recurse -Filter *.streamingsector.json | Select-Object -First 1
& $py -3 -m ncig.cli inspect-city-json --input $one.FullName --out build\sector_inspection.json
```

Useful fields are `data_type`, `node_count`, `nodeData_Data_count`, `sample_node_types` and `parsed_record_count`.

## Important world-data details

CDPR's world is split into many overlapping streaming sectors and LODs; a location can span multiple sectors and different LOD sector grids. citeturn480845view0

Nodes and nodeData are separate tables: a node describes the object, while nodeData describes where each instance is placed. A single node can have multiple placements. citeturn480845view0turn278185search2

This distinction is essential for NCIG because a door, wall or window definition is not useful for building detection until its actual world placement is recovered.
