# NCIG v0.22.8 — city-scale world export pipeline

## Current input format

WolvenKit's JSON representation of a native `worldStreamingSector` uses a top-level `Data` object. Inside it, `nodes` contains distinct node definitions and `nodeData` contains the placement records. Each `nodeData` entry references a node by `NodeIndex`. WolvenKit serializes the `worldNodeDataBuffer` as structured JSON when that buffer type is recognized. citeturn480845view0

NCIG now parses this native structure directly instead of expecting an Object Spawner-style envelope.

## Persistent index

A large export should be indexed once:

```powershell
$py = Get-Command py.exe | Select-Object -First 1 -ExpandProperty Source
& $py -3 -m ncig.cli index-city-world --input C:\CyberpunkExports\sectors --out build\city_world_index.sqlite --manifest-out build\city_world_index_manifest.json
```

The index keeps only entrance, exterior-architecture and interior evidence plus compact transforms, dimensions and sector provenance. The original 90 GB export remains untouched.

Subsequent detection runs can read the SQLite index rather than reparse every sector:

```powershell
& $py -3 -m ncig.cli detect-city-buildings --input build\city_world_index.sqlite --out build\auto_building_candidates.json
```

The automatic preparation script now performs this indexing pass automatically when the database does not already exist.

## Single-sector smoke test

Before indexing the whole city, inspect one exported sector:

```powershell
$one = Get-ChildItem C:\CyberpunkExports\sectors -Recurse -Filter *.streamingsector.json | Select-Object -First 1
& $py -3 -m ncig.cli inspect-city-json --input $one.FullName --out build\sector_inspection.json
```

Useful fields are `data_type`, `node_count`, `nodeData_Data_count`, `sample_node_types` and `parsed_record_count`.

## Detection outputs

- `build\world_manifest.json`
- `build\city_world_index_manifest.json`
- `build\city_world_index.sqlite`
- `build\auto_building_candidates.json`
- `build\auto_buildings.json`
- `build\generated_auto\layouts.json`
- `build\real_architecture_remote\architecture_assembly_auto.json`

## Important world-data details

CDPR's world is split into many overlapping streaming sectors and LODs; a location can span multiple sectors and different LOD sector grids. citeturn480845view0

Nodes and nodeData are separate tables: a node describes the object, while nodeData describes where each instance is placed. A single node can have multiple placements. citeturn480845view0turn278185search2

This distinction is essential for NCIG because a door, wall or window definition is not useful for building detection until its actual world placement is recovered.
# NCIG v0.22.7 — city-scale world export pipeline

## Purpose

v0.22.7 prepares NCIG for a large local export of Night City's compiled/default world sectors.

The city detector is separate from the original small detector so the large-world path can evolve without destabilizing the established building-generation pipeline.

## Input

Use a local directory containing the JSON-converted `.streamingsector` files from the base-game world export, for example:

`C:\CyberpunkExports\sectors`

The loader accepts:

- World Builder/Object Spawner envelopes containing a `sectors` array.
- A direct single-sector JSON with `nodes`.
- A direct single-sector export with `nodes` plus `nodeData` placements.

## City-scale detection

The detector builds an XY spatial grid for:

- entrance clustering;
- nearby exterior architecture lookup;
- existing interior evidence lookup.

This avoids a full pairwise scan of every world node against every entrance.

Existing-interior evidence is tested against the candidate's estimated oriented footprint with a small margin. An interior belonging to a nearby building therefore has less chance of incorrectly suppressing an otherwise valid exterior candidate.

## Outputs

The preparation script writes:

- `build\world_manifest.json` — export inventory and parse health.
- `build\auto_building_candidates.json` — all detected candidates and evidence.
- `build\auto_buildings.json` — selected candidates for generation.
- `build\generated_auto\layouts.json` — generated layouts.
- `build\real_architecture_remote\architecture_assembly_auto.json` — real-asset architecture assembly.

## Recommended workflow

1. Convert/export the complete desired `default` sector tree to JSON once.
2. Keep that data in the local workspace; do not commit it to the public NCIG repository.
3. Run:

```powershell
.\tools\prepare_detected_buildings_remote.cmd https://github.com/Guarrazo/harvest C:\CyberpunkExports\sectors 10
```

The last argument is still a safety cap on generated anchors. The city detector itself analyzes every JSON file under the supplied directory.

The first diagnostic to inspect is `build\world_manifest.json`. If its file/record counts are sensible, inspect `build\auto_building_candidates.json` before increasing the generation cap.
